# Auction and buyback history: bounded event helper

Use `scripts/history.py` for observed license/post-genesis charter round purchases, quantity-weighted event-accounted consideration and observed roll capacity. This is a supported read-only event helper, distinct from the current `snapshot.py auctions` profile, a price-curve model or a planner. The [event catalog](../assets/interfaces/auction-events.json) supplies reviewed event definitions and fixed identities; [source provenance](../assets/sources/live-interface.json), `sr-auction-event-interface`, explains their scope. [Auctions](auctions.md) describes published design, not historical settings. Results are fetched on demand, written only to stdout and never saved by the helper.

The same helper also supports `buybacks`: observed `BuybackExecuted` accounting from the fixed Contraction Vault, not total protocol token burn. Its separate [treasury event catalog](../assets/interfaces/treasury-events.json) uses source provenance `sr-extended-read-interface`. Buybacks are not auction rounds and accept no day filter. The shared finite scanning, canonical-header checks, transport diagnostics and no-persistence rules below apply to both.

## Run a bounded scan

Run from the installed `srstack` root with the host's reviewed Python 3:

```sh
python3 -B -I scripts/history.py license
python3 -B -I scripts/history.py license --day 7 --anchor-block 2000000 --lookback-blocks 1000000
python3 -B -I scripts/history.py charter --from-block 1000001 --to-block 2000000 --chunk-blocks 10000 --max-chunks 100
python3 -B -I scripts/history.py buybacks --lookback-blocks 100000
python3 -B -I scripts/history.py buybacks --from-block 1000001 --to-block 1100000 --chunk-blocks 10000 --max-chunks 10
```

The numbers above are input examples, not saved observations or claims that round 7 occurs there. For auctions, omit `--day` to group every observed round; `--day N` filters the **emitted round identifier**, not a UTC calendar date. It does not narrow the underlying topic query or prove that the round's entire lifetime is in the requested interval. `buybacks --day N` is rejected before any network request.

Without explicit endpoints, `--anchor-block B` is an inclusive upper block; if omitted it is resolved once from a fresh head. `--lookback-blocks N` defaults to **1,000,000 blocks** ending there (clamped at genesis). This is a search span, not an assumption about block rate, elapsed hours or auction duration. Alternatively, supply both inclusive `--from-block A --to-block B`; that form cannot be combined with anchor/lookback flags and uses `B` as the integrity anchor. Historical anchors need not be fresh. The helper does not search for a day automatically or silently widen a range.

Both forms accept `--chunk-blocks N` (default/max **10,000**), `--max-chunks N` (default **100**, max **500**) and `--detail summary|full`. Compact summary is the default. Full detail adds bounded normalized decoded events, including positions and block/transaction hashes, under `evidence.decoded_events`; it does not fetch receipts or add RPC methods. There is no endpoint, address, header, retry, output-file or persistence option.

Only charter purchase events include buyer addresses, exposed with `--detail full`. License purchase events have no buyer field; a charter's current owner cannot establish its historical buyer. Neither purchase event catalog is a record of unsuccessful bids.

Additional non-configurable ceilings are **5,000,000 requested blocks**, **4,096 individual JSON-RPC requests**, **64 MiB total response budget**, **1 MiB per HTTP response**, **10,000 returned logs**, **2,048 headers per window**, **1,000 emitted summary rounds**, **180 seconds overall**, and the shared transport's **10-second request deadline**. A response containing **2,000 or more logs in one window** is conservatively treated as saturated/incomplete, not silently accepted as a full page. If the explicitly requested span exceeds the chosen chunk count, the helper completes only that many chunks and reports the rest missing. Bounds are hard ceilings, not promises that the provider will satisfy them.

Live HTTP requests are spaced at least **0.5 seconds** apart within the same overall deadline, rather than bursting the scan. This is a client request budget, not a claim about the provider's rate limit. A 429 still stops the scan with original-response diagnostics and missing coverage; no automatic retry, wait-and-resume loop or alternate endpoint. Controlled injected test transports do not sleep.

## Read the result

Auction JSON has `schema_version: 1`, `status: "ok"|"partial"`, `auction`, `rounds`, `coverage`, `errors` and `evidence`. Buyback JSON instead has `kind: "buybacks"` and `buybacks`, without auction/round/day-filter fields. Exit codes are **0** for a checked requested window, **4** for partial/unavailable history, and **2** for invalid input (the latter returns `status: "error"` with `error.kind: "input"`). `status: "ok"` means the bounded window passed this helper's checks—not a complete round, independently reconciled asset movement or finality.

- `rounds[].day` is an exact decimal string. `purchase_quantity` is the sum of license counts, or one per charter purchase; `purchase_event_count` is separate.
- `consideration` has `basis: "purchase_event_accounting"`, `asset` (`STANDARD` or `ETH`), `decimals: 18`, exact `total_raw`, scaled decimal `total`, and `quantity_weighted_average_raw: {"numerator": "...", "denominator": "..."}` in the asset's raw units per license/charter. The fraction is reduced exactly. No purchases means the average is `null`, not zero.
- `observed_rolls` and `observed_activations` contain block number, block timestamp and transaction hash; rolls also contain their `reported_cap`. `first_observed_purchase` and `last_observed_purchase` use those same observation fields. Times are Unix seconds from checked headers, never synthetic opening times.
- `reported_round_cap` is available only from a consistent `DayRolled` naming that same day. An activation event or unrelated configuration event cannot supply it. `scheduled_opening` and `time_to_sellout` remain `null`, `complete_round` remains `false`, and `sellout` is `"not_established"`: this event-only helper does not establish effective opening/configuration or a complete round. `gaps` states these limits and any requested-window gaps.
- `coverage.requested` records the resolved inclusive range. `completed` records non-overlapping checked windows, matched-event counts and a checked-header digest; `missing` records the untrusted/unscanned remainder with a reason. A failure before resolving an implicit head leaves unavailable endpoints `null` while `coverage.selection` retains the requested bounds. `coverage.day_filter` is the emitted-ID filter or `null`. Successful empty windows do **not** create zero-sale rounds; an observed activation/roll may produce a round with zero **observed** purchases, never a complete zero-sale claim.
- `errors` identifies the setup, failed window or final-anchor stage. An HTTP denial retains the original bounded `diagnostics` supplied by the shared snapshot transport. No request follows that denial; it is evidence about that request, not proof of global endpoint availability or its underlying cause.
- `evidence` identifies the fixed chain/address/endpoint, catalog hashes, anchor/header/code observations, retrieval UTC, limits and actual request/byte/log counters. `response_bytes` counts returned successful transport byte strings, not the separately bounded original HTTP-failure excerpt. Every request reserves one maximum-size response against the total budget before sending. Per-window anchor/hash checks support retained committed windows after a later ordinary failure. `final_anchor_check` states whether the last check matched, was unavailable or observed a change.

The helper supports useful purchase accounting despite unavailable scheduled openings. It does **not** use current `lastSalePrice`, assume 24-hour rounds, claim sellout or independently reconcile consideration receipts. Those stronger conclusions need the additional evidence below.

### Buyback event accounting

`buybacks.basis` is `buyback_event_accounting`. `event_count` counts only checked `BuybackExecuted` logs, not transactions, transfers, all token burns or current cumulative counters. `eth_spent` sums only the event's `ethSpent`; `standard_burned` sums only `tokensBurned`. Each amount reports `asset`, `decimals: 18`, an exact decimal-integer `total_raw` and a scaled exact decimal `total`: ETH wei and raw 18-decimal STANDARD respectively. No float rounding, swap-price extrapolation, reserve-asset decimal assumption or protocol-wide burn substitution is used.

`first_observed_buyback` and `last_observed_buyback` contain the checked event block number, block timestamp and transaction hash, or `null` when no event is observed. Full detail exposes the individual normalized `ethSpent` and `tokensBurned` raw integer fields under `evidence.decoded_events`. These values are the event's reported accounting, **not independent proof of actual ERC20 movement, successful burn routing, net supply change or holder income**; no receipts, arbitrary token calls or traces are fetched.

The denomination follows the publisher's ETH18 Contraction Vault/pool display and canonical purchased-STANDARD buyback semantics, not the event field names alone. Before scanning, the helper checks `ContractionVault.standard()` against the fixed STANDARD identity and requires that fixed token's nonempty code and `decimals() == 18`, all at the scan anchor. These two zero-argument calls use only the reviewed callable catalog and fixed addresses. `evidence.anchor_standard_binding` records the successful check; failure leaves buyback amounts unavailable and stops before logs. An anchor binding does not prove identical implementation or token relationships throughout the earlier interval.

`observation_status` distinguishes `observed_events`, `no_matches_in_scanned_windows` and `unavailable`. Checked empty windows yield zero **observed** event counts and sums for those windows, never a claim that no buybacks ever happened. If no window can be committed (including after a reorg invalidates earlier windows), the count and amount totals are `null`, not zero. After a later ordinary failure, totals include only `coverage.completed`; the failed window contributes nothing, and `coverage.missing` remains explicit. `requested_range_complete` is false on any error or missing coverage; true still means only that this bounded scan passed its checks, not independently established completeness or finality.

For programmatic use, the buyback selection is `{"schema_version":1,"kind":"buybacks",...bounds}`; existing auction selections remain `{"schema_version":1,"auction":"license"|"charter",...bounds}`. These are distinct selections, not aliases; mixing `kind`, `auction` or a buyback `day` fails before network access. The supported CLI above supplies these fields automatically.

## Authenticate the requested generation

Specify license versus post-genesis charter auctions or Contraction Vault buybacks, chain, finite interval/rounds and requested denomination. The auction kinds are not founding-sale auctions, and buybacks are not a burn-history alias. The reviewed publisher mapping is Robinhood Chain **4663**:

- License auction: `0xA45CE49303EEd5846F841BFd4bAC6aE8C805EC05`; literal ABI `_t`.
- Charter auction: `0x65B4f85b4A64424F6bA0fFe0C535100bc6888892`; literal ABI `mr`.
- Supporting Central Bank: `0x5977B25419f9c0dDcB2F89fE204955622f4F57ea`; literal ABI `_e`, `BranchesOpened` only for receipt-level consideration corroboration.
- Contraction Vault: `0x796e80E8ABcedc30c700A9587F7933d3342B8946`; literal ABI `OC`, `BuybackExecuted(uint256,uint256)` only for the buyback scan.

The official HTML links `app-BzDBLzVV.js`, whose literal import is `mountApp-DmwNsaDC.js`; the HTML also links that mount module directly. Its chain/deployment mapping and complete literal auction/Contraction Vault ABI arrays are the evidence, not the stale older app filename. Follow [bounded source recovery](contracts.md#recover-a-stale-frontend-source-link) if these assets move. Read text only; never execute downloaded JavaScript. Publisher binding authenticates an interface, not independent deployment/source equivalence. A different generation/address needs its own authenticated mapping and events.

## Retrieve a finite, auditable window

The supported helper performs these checks automatically against only `https://rpc.mainnet.chain.robinhood.com/`:

1. After the caller's [trusted-runtime preflight](execution.md#trusted-runtime-preflight) authenticates the sibling script against the reviewed manifest, load literal `scripts/snapshot.py` through a no-follow descriptor read and compile those bytes. The loader checks path, regular-file identity, size and mid-read changes—not content provenance by itself. No user/network input supplies executable bytes, no ambient sibling import or downloaded code is used, and `-I` works without adding the package to `sys.path` or writing bytecode. This reuses transport/parsing/catalog routines, not current-state calls. A locally writable runtime or compromised interpreter remains outside that trust boundary.
2. Validate chain **4663**, event catalog structure and its reviewed contracts/events SHA-256 fingerprint; cross-check entity IDs and fixed addresses against the existing reviewed callable/entity catalogs. Check the anchor header and nonempty contract code at that anchor. Buybacks additionally require the fixed STANDARD binding, code and 18-decimal denomination checks described above; auction scans do not add these state calls. Code presence and publisher-bound ABI identity are not independent source/bytecode equivalence or proof that earlier generations used the same implementation.
3. Issue explicit ascending, non-overlapping inclusive chunks for one fixed address and its catalog topic-zero OR filter. Auction scans decode purchase, activation/roll and reviewed configuration/pause/ownership events; the Central Bank supporting event is not queried as another auction target. Day filtering is local after strict decoding, avoiding incompatible indexed positions among the event types. Buyback scans instead query only the Contraction Vault and `BuybackExecuted`; they never query auction, token `Transfer` or protocol-wide burn events.
4. Enforce per-request, total-byte, request-count, log-count, header-count, round-count, span/chunk and time ceilings. There is no retry, alternate source, automatic splitting or failed-window skip. A provider error, malformed result or conservative saturation threshold stops at that window and reports the remaining range. A smaller window is a new explicitly chosen run, not hidden pagination.
5. Require the selected emitter, allowed topic, exact topic/data sizes, supported ABI word types and zero-padded address words. Validate canonical RPC quantities, block range, nonzero hashes, boolean `removed`, log/transaction position order and uniqueness. Duplicate/conflicting log positions are errors, not extra purchases. Conflicting transaction/block identities are never merged.
6. Retrieve canonical-number headers for each event block and both window boundaries; attach only matching block timestamps. Re-read those headers plus the fixed anchor before committing a window. Check the anchor again at successful completion. A removed log or observed reorg excludes untrusted observations and invalidates all previously committed windows, which are listed under `evidence.invalidated_windows`; coverage then marks the requested range missing. No confirmation-depth or finality assumption is made.

An ordinary later failure preserves already checked windows and their event-accounted purchases or buybacks; the failed window is not partly summed. If the final anchor request alone is unavailable, the result is partial, previous per-window checks remain explicit and no stronger final check is claimed. A successful provider response can still silently omit logs; RPC consistency checks are not an independent completeness proof. The helper neither fabricates missing pages nor claims to detect undocumented truncation below its conservative threshold.

For **additional manual research**, retain bounded receipt/state evidence only in the session, never in installed resources. Historical calls must remain pinned; archive errors cannot fall back to `latest`. A receipt can corroborate consideration only through successful execution and authenticated matching events, without double counting. There is no packaged receipt/accounting fallback.

## Reconstruct rounds without assuming 24 hours

Group by `(chainId, auction address/generation, emitted day)`. Here `day` is a contract round identifier, not a UTC date and not proof of a 24-hour interval. Use the round's evidenced opening and ending rules, activation/anchor, duration, pauses and configuration transitions; do not apply today's `AUCTION_DAY`, cap, floor, half-life or owner policy to earlier rounds.

`AuctionStarted(day,startPrice)` is an activation marker. `DayRolled(day,startPrice,floorPrice,cap)` supplies a reported round's price parameters and capacity, but **neither event contains a timestamp, duration or closing reason**. A roll can be processed in a later transaction: its block timestamp is the observed roll time, not automatically the scheduled opening. The first purchase time is also not the opening. The reviewed ABIs contain no dedicated `AuctionEnded` or `SoldOut` event. Do not fabricate either or assume every round emits a roll when its clock expires.

Obtain the actual opening/expiry anchor from authenticated implementation semantics plus interval-specific state/events, or an original source that explicitly establishes it. Historical calls must stay pinned; an archive error cannot fall back to `latest`. Where only a roll observation is available, label it **observed roll transaction**, leave scheduled opening/expiry unavailable and still report supported purchases. Gaps in day IDs are unresolved rounds until activation, skipped/lazy rolls, no purchases, migration and coverage are distinguished; do not synthesize zero rows.

Use `DayRolled.cap` only for the round it names. `AuctionStarted` omits cap; first-round capacity needs separate historical evidence. `LicensesPerDaySet`/`ChartersPerDaySet`, decay/floor/reserve settings and controller events are change evidence, not proof of their effective round. If implementation or historical state is unavailable, do not guess whether a change affects the open round or the next one. A present `soldToday`, `remainingToday` or `lastSalePrice` is not a historical table.

## Quantities, actual consideration and sellout

- **Licenses:** sum `LicensesPurchased.count`, not transaction/event count. Retain each executed `unitPrice` in raw 18-decimal STANDARD; event-accounted consideration is `count × unitPrice`. Where available, corroborate it against the same successful receipt's publisher-bound `BranchesOpened(charterId,count,cost)`, matching charter, quantity and ordering without reusing one cost event. `cost` is the reported total STANDARD ledger charge; do not add it a second time. If receipts or the historical Bank relationship are unavailable, label the result purchase-event accounting rather than independently reconciled payment. A matching event is not proof of ERC20 movement, burn routing or holder income.
- **Charters:** each `CharterPurchased` represents one charter; `price` is its reported executed consideration in ETH wei. Do not substitute transaction `value`, a maximum-price input, refund-inclusive funding or a current quote. Further payment reconciliation requires authenticated receipt/event semantics and an available public endpoint; no state-changing simulation or tracing workaround.
- **Weighted average:** `sum(actual consideration) / sum(licenses)` for licenses, or total executed ETH consideration divided by purchased charters. Weight every multi-license purchase by quantity; never take the arithmetic mean of event unit prices. Use integer/rational arithmetic from unrounded raw values and round only for presentation. A zero denominator makes the average undefined, not zero. If only event-accounted consideration is established, name the average accordingly rather than claiming independently reconciled actual payments.
- **Sellout:** complete purchase coverage from the evidenced round opening, the historically applied cap and any effective changes must establish the first purchase that exhausts capacity. Reconcile without double counting; a partial log count equal to today's cap is not enough. The last observed purchase need not be the sellout. If the historical cap or earlier purchases are missing, sellout remains not established.
- **Time to sellout:** compute sellout block time minus **evidenced opening time** only when both endpoints and their semantics are established. Otherwise report available first/last purchase or observed-roll times with those labels, not “sold out in N hours.” Observations at block granularity are not sub-block wall-clock timings. No sellout means no opening-to-sellout duration; expiry and sellout are different outcomes.

## Report supported scope, not a fictional recap

A useful per-round result has round/generation, opening/end anchors (or explicit gaps), historically applied cap, purchase count, license/charter quantity, denomination, total executed consideration, quantity-weighted average, first/last purchase, sellout status/time and coverage status. Omit unrequested columns. Preserve raw inputs, source URLs, block/transaction hashes and calculations in the session or answer; never save a financial recap as a package fallback.

Public logs and successful receipts can support purchase accounting even when historical state cannot be read. Archive access, opening/expiry semantics, payment reconciliation and source/bytecode correspondence each need their own evidence for the requested interval. If an endpoint or definition is unavailable, name exactly which conclusion it prevents and retain supported partial facts. Do not infer an unavailable historical API, fake an opening time or use the current helper as a substitute. Fetch results on demand; store no historical observations or validation examples in the skill.
